# 이지엣지 사용자 매뉴얼

이지엣지는 Zendesk에 새로 들어온 문의를 읽고, 담당 파트·세부업무·개발 담당자와 그날 젠콜 PIS 담당자를 정해 Telegram으로 알려 주는 사내 웹 도구입니다. 이 매뉴얼은 PIS팀과 운영 담당자가 쓰는 화면을 탭 순서대로 설명합니다.

## 접속

- 주소는 운영 담당자가 안내한 사내 주소를 사용합니다.
- **Zendesk로 로그인**을 누르고 평소 쓰는 Zendesk 계정으로 로그인합니다. 상담원·관리자 계정만 들어올 수 있습니다.
- **웹 로그인과 접수 계정은 별개입니다.** 티켓 조회와 실제 접수(양식·필드·상태 변경, 공개 안내)는 **접수 계정** 이름으로 Zendesk에 기록됩니다.
- 웹 로그인은 여러 명이 동시에 할 수 있습니다.
  - 화면 로그인은 12시간 뒤 끝나며, 오른쪽 위 **로그아웃**은 그 브라우저만 로그아웃합니다. 접수 계정과 자동 접수는 그대로입니다.
- 접수 계정은 서버에 한 명입니다.
  - 접수 계정이 없을 때 처음 로그인한 사람이 맡습니다. 브라우저를 닫아도 자동 접수는 계속됩니다.
  - 바꾸려면 설정(06) 'Zendesk 접수 계정'의 **내 계정을 접수 계정으로 지정**을 누르고 Zendesk 로그인을 한 번 더 합니다. 이전 계정은 해제됩니다.
  - **자동 접수 멈추기**로 접수 계정을 해제하면 다시 지정할 때까지 **자동 접수가 멈춥니다.**
- Zendesk 로그인 설정(아래 '06 연결 및 설정') 전에는 관리자 비밀번호로 로그인하고, 서버 `.env`의 API 토큰 계정으로 접수합니다.
- 화면 오른쪽 위에 **추천 전용** 또는 **실제 접수**가 표시됩니다. **실제 접수**일 때는 이지엣지가 Zendesk 티켓을 직접 변경합니다.

## 자동으로 일어나는 일

**연결 및 설정 → 자동화**에서 자동 수집, Claude 분석, Telegram 알림이 켜져 있으면 1분마다 신규 티켓을 확인합니다. 사람이 누를 것은 없습니다.

1. Claude가 문의를 요약하고 **파트와 세부업무**를 고릅니다.
2. **업무·담당자 기준**에서 그 세부업무의 개발 담당자를 찾습니다. 주담당이 부재·비활성이거나 권장 업무량을 넘었으면 백업에게 배정합니다.
3. **운영 달력**의 그날 젠콜 중에서 PIS 담당자 한 명을 정합니다.
4. Telegram으로 알립니다. 실제 접수가 켜져 있으면 Zendesk에도 반영합니다.
   - Telegram 전송이 실패했거나 결과를 확인하지 못한 티켓에는 **알림 전송 실패·미확인** 표시와 **알림 재전송** 버튼이 생깁니다. 카드 위쪽에는 **알림 전송 실패 N건**(없으면 0건)이 항상 표시되고, 1건 이상이면 **전송 실패 알림 모두 재전송** 버튼이 생깁니다. 이 버튼은 그런 건을 한꺼번에 다시 보냅니다. 분석·배정·Zendesk는 바뀌지 않고 Telegram 메시지만 다시 보냅니다. 응답 지연으로 실패한 건은 이미 대화방에 도착했을 수 있으니 대화방을 확인한 뒤 누르세요.

미리 해 둘 일은 두 가지입니다. **기준표를 최신으로 유지하는 것**, 그리고 **달력에 젠콜을 넣어 두는 것**입니다.

## 01 접수 현황

티켓별 처리 결과를 봅니다.

| 상태 | 뜻 |
| --- | --- |
| 추천 완료 | 검토 사유가 없습니다. 실제 접수 모드에서는 Zendesk에 반영을 시도합니다 |
| 검토 필요 | 사람이 확인해야 합니다. **근거** 칸에서 이유를 확인하세요 |
| 운영일 대기 | 운영 시간 외에 들어와 다음 운영 시간에 처리합니다 |
| 재시도 대기 | 분석 중 오류가 나서 다음 주기에 다시 시도합니다(최대 3회) |
| 대상 제외 | 이미 신규 상태가 아닙니다 |

**PIS** 칸에는 배정된 PIS 담당자와 Zendesk 접수 결과가 표시됩니다.

| 접수 결과 | 뜻과 할 일 |
| --- | --- |
| 접수 완료 | Zendesk 반영이 끝났습니다 |
| 접수 보류 | 반영 조건을 만족하지 않아 **변경하지 않았습니다**(예: 다른 양식이 이미 지정됨). 근거를 보고 Zendesk에서 직접 접수하세요 |
| 접수 실패(변경 없음) | Zendesk가 거부했습니다(예: 그 사이 다른 사람이 수정). 직접 접수하거나 **재분석**하세요 |
| 접수 결과 미확인 | 응답을 받지 못해 반영 여부를 모릅니다. **다시 보내지 않습니다.** **결과 확인**을 눌러 확정하고, 그래도 모르면 Zendesk에서 직접 확인하세요 |

## 02 운영 달력

### 운영 시간과 휴일

- **운영 시간**: 시작·종료 시간과 주말·공휴일 제외 여부를 정합니다.
- **날짜별 예외**: 사내 휴무일은 '자동 접수 제외', 주말·공휴일에 운영하는 날은 '운영 허용'으로 등록합니다.

달력 칸에는 휴일 표시, **초록색 PIS 젠콜 이름**, **회색 개발 담당자 부재**가 보입니다. 날짜를 누르면 아래 젠콜 표의 그 날짜로 이동합니다.

### PIS 젠콜 등록

**젠콜 담당자가 등록되지 않은 날에는 PIS를 배정하지 않습니다.** 그날 티켓은 PIS 없이 '검토 필요'로 남으니, 한 달 치를 미리 넣어 두세요.

**방법 1. 배정표 스크린샷으로 채우기**

1. **배정표 스크린샷**에서 이미지(PNG·JPEG·WebP, 5MB 이하)를 고르고 연도를 확인합니다.
2. 비용 안내에 체크하고 **스크린샷 읽어서 채우기**를 누릅니다. 최대 2분 정도 걸립니다.
3. 인식된 날짜의 드롭다운이 채워지고 노란색('저장 전')으로 표시됩니다. **아직 저장된 것이 아닙니다.**
4. 원본과 비교합니다.
   - **확인** 칸에 표시가 있으면 꼭 보세요. 예: `명단에 없는 이름`, `call1 칸에 여러 이름`, `중복된 이름`.
   - 연차 등 부재로 인식된 사람은 **부재**에 체크되어 있습니다.
   - 틀린 칸은 드롭다운에서 바로 고칩니다.
5. 날짜가 불명확하거나 `#VALUE!` 같은 오류가 있던 행은 **날짜 확인 필요** 목록에 따로 나옵니다. 원본에서 날짜를 확인한 경우에만 날짜를 고르고 **이 날짜에 넣기**를 누르세요.
6. **젠콜 저장**을 누릅니다. 취소하려면 **저장 전 변경 취소**를 누릅니다.

**방법 2. 드롭다운으로 직접 고르기**

날짜 행에서 call 1·2·3 담당자를 고르고, 갑자기 빠지는 사람은 **부재**에 체크한 뒤 **젠콜 저장**을 누릅니다. 저장한 직후부터 반영됩니다.

**PIS 배정 방식**

- 티켓이 한 건씩 들어오면, 그날 젠콜 중 **그날 배정 비율에 비해 오늘 배정이 가장 부족한 사람**에게 배정합니다. 비율은 달력 표의 call 칸마다 %로 넣고, 부재가 아닌 젠콜 담당자의 합계가 100%여야 저장됩니다. 40·30·30%면 10건 중 대략 4·3·3건이고, 모두 비워 두면 똑같이 나눕니다. 스크린샷으로 채운 날은 비율이 비어 있으니 필요하면 직접 넣으세요.
- 젠콜이 아닌 사람, 부재인 사람, 비활성인 사람에게는 **절대 배정하지 않습니다.**
- 검토가 필요한 티켓을 포함해 분석한 모든 티켓에 PIS를 한 명 배정합니다.
- **연결 및 설정**의 '밀린 티켓 묶음 기준'이 1 이상이고 한 번에 그 건수 이상이 쌓이면, 기준표의 **PIS 담당 → PIS 백업** 순서로 한 사람에게 한 건씩 배정합니다. 그래도 남는 티켓은 그날 배정 비율 순서로 계속 배정합니다.

### 개발 담당자 부재

담당자, 기간, 사유를 넣고 **부재 저장**을 누릅니다. 기간 중에는 기준표의 주담당 대신 백업에게 배정합니다.

## 03 업무·담당자 기준

**누가 어떤 업무를 맡는지는 이 표 하나로 정합니다.** 구조는 **파트 → 세부업무 → 개발 담당·개발 백업 / PIS 담당·PIS 백업**입니다.

1. 위쪽 파트 버튼에서 파트를 고릅니다. 버튼의 숫자는 세부업무 개수입니다.
2. **파트 기본** 행은 세부업무가 없거나 Claude가 세부업무를 고르지 못했을 때 쓰는 담당자입니다. **모든 파트에 채워 두는 것을 권장합니다.**
   - 파트 기본 담당자도 비어 있으면, 비슷한 과거 티켓을 **실제로 처리한 개발 담당자**를 추천하고 검토 필요로 둡니다. 사유에 `과거 유사 티켓 #번호 처리자 (기준표 담당 없음)`이 표시됩니다.
   - 기준표에 담당자가 있으면 과거 처리자보다 기준표를 따릅니다. 과거 완료 티켓으로 확인했을 때 기준표 담당자가 더 정확했습니다(원무 88% 대 71%).
3. 세부업무 행마다 담당자를 드롭다운에서 고릅니다. 세부업무 이름 아래 **판단 기준**(키워드·화면명)은 Claude가 세부업무를 고를 때 참고합니다. 쓰지 않는 세부업무는 **사용** 체크를 해제합니다.
4. **세부업무 추가**, **삭제**, **파트 추가**, **이 파트 삭제**, 파트 이름 변경도 여기서 합니다. 파트 이름을 바꾸면 그 파트의 세부업무도 함께 옮겨집니다.
5. 다 고쳤으면 **기준 저장**을 누릅니다. **다음 분석부터 바로 반영됩니다.**

- 드롭다운에 `(명단에 없음·확인 필요)`가 보이면 명단에 없는 이름입니다(예: `도혜미`, `조한슬(데이터쿼리)`). 명단에 있는 사람으로 바꾸세요.
- **개발 담당자 명단**: 활성 여부와 권장 업무량(미해결 티켓이 이만큼 쌓이면 백업에게 배정)을 정합니다.
- **PIS 명단**: 활성 여부를 정합니다. 배정 비율은 운영 달력에서 날짜별로 정합니다.

## 04 추천 테스트

1. 가상 병원과 문의 내용을 입력합니다. 환자정보는 넣지 마세요.
2. PIS 담당자는 기본값 **자동 선택**이면 테스트 일시의 젠콜 기준으로 고릅니다(실제 배정 건수에는 더하지 않습니다).
3. Telegram 전송에 체크하면 `[테스트]`가 붙은 메시지를 보냅니다.
4. 결과에서 요약, 파트·세부업무, 개발 담당자, PIS, **운영팀 담당자 필드 예상**을 확인합니다.

테스트는 실제 Zendesk를 읽거나 바꾸지 않지만 Claude 호출 비용은 발생합니다.

## 05 검토·정확도

자동 접수가 실제로 맞았는지 확인하고, 틀린 부분을 고쳐 정확도를 높이는 화면입니다.

1. **접수 자료 업로드**에 개발팀·젠콜 접수 현황 XLSX(티켓번호, 요청병원, 관련파트, 개발담당자/PIS담당자, 요청내용요약, Zendesk 실제상태 열)를 올립니다. 같은 파일로 과거 사례 검색 자료도 교체됩니다.
2. 처리완료 티켓마다 **첫 자동 추천**과 **실제 기록**을 비교해 분류합니다.

| 결과 | 뜻 | 활용 |
| --- | --- | --- |
| 일치 | 파트와 담당자가 맞았습니다 | — |
| 파트 오분류 | 추천 파트가 실제 파트와 하나도 겹치지 않습니다 | 프롬프트 개선 사례 |
| 담당자 변경 | 파트는 맞지만 실제 처리자가 달랐습니다 | 기준표 변경 제안 |
| 실제 담당 정보 없음 / 자동 추천 이력 없음 | 비교할 수 없습니다 | — |

3. **기준표 담당자 변경 제안**: 같은 세부업무에서 다른 사람이 반복해서 처리했다면 보여 줍니다. 부재나 업무량 조정 때문일 수도 있으니 확인한 뒤 **주담당으로 변경**을 누르세요. 실제 처리자가 현재 백업이면 주담당과 백업을 맞바꿉니다.
4. **프롬프트 개선**: **개선 후보 생성**을 누르면 최근 파트 오분류 사례(최대 12건)로 후보를 만듭니다. 사례를 펼쳐 확인한 뒤 **적용**하면 이후 문의부터 Claude가 참고합니다. 문제가 있으면 **기본 프롬프트로 복원**합니다.
5. **프롬프트 버전별 정확도**: 적용 후 새로 쌓인 티켓을 다시 업로드하면 버전별 파트·담당자 정확도를 비교할 수 있습니다. 건수가 적을 때는 차이를 단정하지 마세요.
6. 자료가 잘못 기록된 티켓은 **제외**하면 정확도와 개선 사례에서 빠집니다.

## 06 연결 및 설정 (운영 담당자용)

- **자동화**: 자동 수집, Claude 분석, Telegram 알림, 첨부 확인(기본 꺼짐. 켜면 본문만으로 판단이 어려운 티켓만 첨부 이미지·PDF 최대 3개를 Claude로 보내 다시 분석합니다. 이미지 속 환자 정보는 지워지지 않습니다), AI 신뢰도 기준(AI가 매긴 신뢰도가 이 값보다 낮으면 검토 필요), 밀린 티켓 묶음 기준, 접수 안내 문구, 실제 접수 스위치.
- **Zendesk 필드 · 양식 · 상태**: 병원명·요청부서·관련파트·운영팀 담당자 필드 ID, `데이터 서비스` 양식 ID, `등록` 사용자 지정 상태 ID.
- **Zendesk 선택값**: 파트·개발·PIS마다 Zendesk 옵션 값을 한 표에서 입력합니다. **접수 사전 점검**을 누르면 설정 오류와 옵션 이름이 같은 값을 보여 주고, **일치한 값 채우기** 후 **선택값 저장**으로 저장합니다.
- **Claude 모델 · Zendesk 접수 계정** (접수 계정은 지금 로그인한 사람으로 표시만 됩니다)
  - 모델: 티켓 분석용과 이미지 분석용(배정표 스크린샷·티켓 첨부) 모델, 사고량을 고릅니다. '.env 값 사용'을 고르면 .env를 따릅니다. 저장하면 다음 분석부터 바로 적용됩니다.
  - 접수 계정이 바뀌면 **접수 사전 점검**을 다시 실행하세요.

### Zendesk 로그인 설정 (처음 한 번, Zendesk 관리자)

Zendesk API 토큰은 2026-10-27부터 새로 만들 수 없고 2027-04-30에 모두 사용 중지됩니다. 그 전에 OAuth 로그인으로 바꿔야 합니다.

1. Zendesk 관리 센터 → **앱 및 통합 → API → OAuth 클라이언트 → OAuth 클라이언트 추가**.
2. **허용 범위(스코프)**에 **전체 읽기(`read`)**와 **티켓 쓰기(`tickets:write`)**를 켭니다. 빠지면 로그인 때 `Invalid scope`가 뜹니다. 신규 티켓 검색은 티켓 읽기 같은 세부 읽기 권한으로는 막히므로 전체 읽기가 필요합니다. 권한을 바꾼 뒤에는 로그아웃 후 다시 로그인해야 새 권한이 적용됩니다.
3. 이름은 `이지엣지`, 클라이언트 종류는 **기밀(Confidential)**, 리디렉션 URL은 `<이지엣지 주소>/auth/callback`을 넣습니다. 예: `https://easyedge.사내도메인/auth/callback`. 다른 PC에서도 접속하므로 https 주소를 권장합니다.
4. 저장할 때 한 번만 보이는 **시크릿**과 **고유 식별자**를 서버 `.env`에 넣습니다.
   - `ZENDESK_OAUTH_CLIENT_ID=<고유 식별자>`
   - `ZENDESK_OAUTH_CLIENT_SECRET=<시크릿>`
   - `PUBLIC_URL=<이지엣지 주소>` (3번의 리디렉션 URL에서 `/auth/callback`을 뺀 값과 정확히 같아야 합니다)
5. 서버를 다시 켜면 로그인 화면이 **Zendesk로 로그인**으로 바뀝니다. 로그인한 뒤 접수 사전 점검을 실행합니다.
6. 로그인이 확인되면 `.env`의 `ZENDESK_API_TOKEN`은 지우고, Zendesk 관리 센터에서 그 토큰을 비활성화합니다.
- **Google Sheets 연결**.

### 실제 Zendesk 접수 켜기

실제 접수를 켜면 검토 사유가 없는 신규 티켓마다 다음을 한 번에 반영합니다.

1. 티켓 양식 → `데이터 서비스`
2. 관련파트 → 추천 파트
3. 운영팀 담당자 → PIS 1명 + 개발 담당자 N명
4. 상태 → `등록`
5. 공개 접수 안내 (`[티켓번호]`는 실제 번호로 바뀜)

켜기 전에 필드·양식·상태 ID를 저장하고, 사전 점검에 오류가 없는지, 선택값이 모두 채워졌는지 확인합니다. 시험 계정에서 먼저 확인한 뒤, 서버 `.env`의 `ALLOW_LIVE_WRITES=true`와 **실제 Zendesk 접수** 체크를 모두 켜야 동작합니다.

**검토 필요여도 접수**: 이 스위치를 켜면 '검토 필요' 티켓도 등록 상태로 바꾸고 접수 안내를 보내며 담당자를 넣습니다. 개발 담당자를 정하지 못한 티켓은 PIS만 넣고, 긴급 의심 티켓('개인정보 유출'·'랜섬웨어'·'진료 전면 중단' 같은 키워드, 또는 AI 판단)도 접수하고 텔레그램에 [긴급]을 붙입니다. 접수 후 검토 사유는 사람이 확인해 담당자를 고칩니다.

**테스트 대상만 실제 접수하기**: '자동화' 카드의 **테스트 티켓 번호**나 **테스트 병원명**(예: `본원_1`)에 하나라도 값이 있으면, 그 티켓과 그 병원 티켓만 실제로 바뀌고 다른 티켓은 추천만 합니다. 화면 위쪽에 `실제 접수 (테스트 대상만)`이 표시됩니다.

- 병원명은 Zendesk 병원명 드롭다운의 옵션 이름으로 적습니다. 이지엣지가 옵션 목록에서 실제 저장값(`본원_1` → `본원`)을 찾아 비교하며, 옵션 목록을 읽지 못하면 어떤 티켓도 바꾸지 않습니다.
- 테스트 대상 티켓은 접수 현황의 **테스트 접수** 버튼으로 '검토 필요'여도 접수할 수 있습니다. 신규 상태·감지 후 미수정·필드 빈 값 같은 다른 확인은 그대로 합니다.
- 테스트 중 분석된 다른 실제 티켓은 나중에 자동 접수되지 않습니다. 사람이 접수하세요.
- **두 칸을 모두 비우면 모든 신규 티켓이 실제 접수 대상**이 됩니다.

다음 경우에는 티켓을 바꾸지 않고 '검토 필요'로 남깁니다.

- 검토 사유가 하나라도 있는 추천
- PIS가 정확히 1명이 아니거나 개발 담당자가 없음
- 담당자·파트의 Zendesk 선택값이 설정되지 않음
- 반영 직전 다시 읽었을 때 신규 상태가 아니거나, 처음 발견한 뒤 누군가 티켓을 수정함
- 관련파트나 운영팀 담당자 필드에 이미 값이 있음
- 다른 양식이 이미 지정되어 있음 (양식이 비어 있거나 계정 기본 양식인 신규 티켓만 바꿉니다)

끌 때는 **실제 Zendesk 접수** 체크를 해제하고 저장하면 다음 주기부터 멈춥니다.

## 서버를 다시 시작할 때

설정은 Google Sheets와 서버에 저장되어 재시작해도 그대로 남습니다. 자동 수집이 켜진 상태로 재시작하면 바로 조회·분석·알림이 다시 시작되고, 실제 접수가 켜져 있으면 Zendesk 변경도 다시 시작됩니다. 점검 중이라면 먼저 자동 수집을 꺼 두세요.
