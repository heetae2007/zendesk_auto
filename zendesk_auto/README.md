# 이지엣지 — Zendesk 문의 자동 접수

Zendesk 신규 문의를 1분마다 조회해 Claude로 요약·파트·세부업무를 분석하고, 기준표에 따라 개발 담당자와 당일 젠콜 PIS 담당자 1명을 정해 Telegram으로 알리는 사내 웹 도구입니다. 설정은 Google Sheets에, 실행 이력은 서버의 `data/`에 저장합니다. 이 저장소는 **0.11** 구현입니다.

> 기본값은 **추천 전용**입니다. 실제 Zendesk 접수(양식·관련파트·운영팀 담당자·상태 변경과 공개 안내 등록)는 서버 `.env`의 `ALLOW_LIVE_WRITES=true`와 웹의 **실제 Zendesk 접수** 설정이 **모두** 켜졌을 때만 동작합니다. 실제 운영 계정에서는 아직 검증하지 않았습니다.

사용 방법은 [사용자 매뉴얼](docs/MANUAL.md)을 참고하세요.

## 처리 흐름

1. 운영 시간(기본 평일 09:00~18:00, 한국 시간)에 Zendesk에서 **신규** 티켓을 조회합니다. 주말·한국 공휴일·지정한 제외일과 운영 시간 외에 들어온 티켓은 다음 운영 시간에 처리합니다.
2. Claude가 문의와 비슷한 과거 사례를 보고 요약, 하나 이상의 **파트**, 파트별 **세부업무**를 정합니다. Claude는 사람을 고르지 않으며, 기준표에 없는 파트·세부업무를 반환하면 응답을 거부하고 재시도합니다(3회 실패 시 검토 대상).
3. **업무·담당자 기준표**에서 개발 담당자를 정합니다.
   - 세부업무의 주담당을 배정하고, 주담당이 부재·비활성·권장 업무량 초과이면 백업을 배정합니다.
   - 세부업무가 없거나 Claude가 고르지 못하면 **파트 기본** 담당자를 배정합니다.
   - 여러 세부업무가 해당하면 개발 담당자도 여러 명이 될 수 있습니다.
4. **운영 달력**의 당일 젠콜 중에서 PIS 담당자를 정확히 한 명 정합니다(아래 PIS 배정).
5. Telegram으로 알리고, 실제 접수가 켜져 있으면 Zendesk에 반영합니다.

검토 사유가 하나라도 있으면 '검토 필요'로 남기고 Zendesk는 변경하지 않습니다. 사유는 웹에서 확인합니다.

## 주요 규칙

### PIS 배정

- 운영 달력에서 날짜마다 call 1·2·3 담당자를 고르고 부재를 체크합니다. 배정 비중은 PIS 명단에서 사람별로 정합니다.
- 배정표 스크린샷은 Claude 이미지 분석으로 읽어 드롭다운에 채우며, **젠콜 저장**을 누르기 전에는 적용되지 않습니다. 날짜가 불명확하거나 `#VALUE!` 등 오류가 있는 행은 날짜를 추정하지 않고 '날짜 확인 필요' 목록에 둡니다.
- **실시간 배정**: 당일 젠콜이면서 부재가 아닌 활성 인원 중, 비중 대비 당일 배정 건수가 가장 부족한 사람을 고릅니다.
- **밀린 티켓 배정**: '밀린 티켓 묶음 기준'(기본 0=사용 안 함) 이상이 한 번에 대기하면, 기준표 세부업무(없으면 파트 기본)의 PIS 담당 → PIS 백업 순으로 같은 묶음에서 한 사람당 한 건씩 배정합니다. 남는 티켓은 당일 젠콜 중 비중 순서로 계속 배정합니다.
- 분석한 모든 티켓(검토 대상·분석 실패 포함)에 PIS를 배정합니다. 젠콜이 아니거나 부재·비활성인 사람에게는 절대 배정하지 않으므로, 당일 젠콜이 없으면 PIS 없이 검토 대상이 됩니다.
- 배정 이력은 티켓당 한 줄로 저장해 재분석해도 중복 집계되지 않습니다.

### 개발 담당자 배정

- 권장 업무량은 미해결 티켓의 운영팀 담당자 필드에 그 사람의 Zendesk 선택값이 들어간 건수로 셉니다. **선택값이 설정되지 않은 담당자는 업무량이 0으로 집계됩니다.**
- `윤세라`·`윤새라`는 기준표에 있어도 배정하지 않습니다(같은 사람인지 확인되지 않아 둘 다 제외).
- `사전심사 화면/창/메뉴`가 명시된 문의는 원무 1명·보험 1명을 배정합니다.

### Telegram

```text
[병원명] 파트 개발담당자 책임님 / PIS PIS담당자 책임님

문의 요약

티켓: #번호
```

여러 파트·담당자는 모두 표시하고, 주담당·협업·검토 필요 문구는 넣지 않습니다. 테스트 메시지에는 `[테스트]`와 '가상 티켓 (실제 Zendesk 티켓 아님)'이 붙습니다.

### 실제 Zendesk 접수 (켰을 때만)

- 검토 사유가 없는 신규 티켓에 `데이터 서비스` 양식, 관련파트, 운영팀 담당자(PIS 정확히 1명 + 개발 N명), `등록` 상태, 공개 접수 안내를 **한 번의 요청**으로 반영합니다. 안내 문구의 `[티켓번호]`는 실제 번호로 바뀝니다.
- 반영 직전 티켓을 다시 읽어 다음 중 하나라도 해당하면 변경하지 않고 검토 대상으로 둡니다.
  - 신규 상태가 아님
  - 최초 감지 이후 수정됨
  - 관련파트·운영팀 담당자 필드에 이미 값이 있음
  - 다른 양식이 지정됨(양식이 비어 있거나 계정 기본 양식인 경우만 변경)
  - 파트·담당자의 Zendesk 선택값이 없음
- Zendesk safe update(`safe_update`, `updated_stamp`)로 그 사이 사람이 수정하면 409로 거부됩니다.
- 티켓당 한 번만 시도합니다. 타임아웃 등 결과가 불확실하면 재시도하지 않고 '접수 결과 미확인'으로 두며, **결과 확인** 버튼으로 티켓을 다시 읽어 확정합니다.

### 검토·정확도

- 개발팀·젠콜 접수 현황 XLSX(티켓번호·요청병원·관련파트·개발담당자/PIS담당자·요청내용요약·Zendesk 실제상태 열)를 올리면, 각 티켓의 **첫 자동 추천**과 실제 기록을 비교해 일치 / 파트 오분류 / 담당자 변경으로 분류합니다. 처리완료 티켓만 정확도에 포함합니다.
- 파트 오분류 사례(최근 12건)로 프롬프트 개선 후보를 만들고, 같은 세부업무에서 다른 사람이 반복해서 처리한 경우 기준표 주담당 변경을 제안합니다. 둘 다 확인 후 적용 버튼으로만 반영됩니다.
- 프롬프트 버전별 정확도로 적용 전후를 비교합니다. 같은 파일로 과거 사례 검색 자료도 교체합니다.
- 이지엣지가 자동 추천한 기록이 있는 티켓만 비교할 수 있습니다.

## 설치와 실행

Ubuntu 등 Linux와 Python 3.11 이상이 필요합니다. 아래 명령은 이 README가 있는 폴더에서 실행합니다.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.lock.txt
cp .env.example .env
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8080 --workers 1
```

브라우저에서 `http://127.0.0.1:8080`으로 접속합니다. 사용자명은 `admin`, 비밀번호는 `.env`의 `ADMIN_PASSWORD`(16자 이상)입니다.

- 단일 관리자 계정·HTTP Basic 인증 구조입니다. 팀원에게 공유할 때는 사내망 접근 제한과 HTTPS(`deploy/nginx.conf.example` 참고)를 적용하세요.
- `--workers 1`과 `data/instance.lock`으로 한 서버의 중복 실행을 막습니다. **여러 서버에서 같은 Zendesk·시트로 동시에 실행하면 중복 배정·접수가 발생할 수 있으므로** 한 대에서만 실행하세요.
- 서버를 켜면 저장된 설정이 그대로 적용됩니다. 자동 수집이 켜져 있으면 Zendesk 조회, Claude 호출, Telegram 전송이 바로 재개되고, 실제 접수가 켜져 있으면 Zendesk 변경도 재개됩니다.

## 저장 위치

- **Google Sheets `Settings` 탭**(한 셀의 JSON): 운영 설정, 파트(`parts`: 파트 기본 담당자·Zendesk 선택값 포함), 세부업무 기준(`work_mappings`), PIS 명단(`pis_members`), 날짜별 젠콜(`pis_days`), 개발자 부재(`absences`), Zendesk 필드 매핑(`mapping`), 실제 접수 설정(`live_writes`).
  - 한 셀 50,000자 제한 때문에 14일이 지난 젠콜 일정은 저장할 때 정리되고, 설정이 45,000자를 넘으면 저장을 거부합니다.
  - 개발 담당자 명단은 `Agents`, 날짜 예외는 `Calendar`, 병원 표시값은 `Hospitals` 탭에 저장됩니다. `Rules`·`Roster`·`Feedback` 탭은 0.11부터 쓰지 않습니다(비어 있음).
- 서버를 켜면 즉시 Sheets에서 설정을 읽습니다. 연결하지 못하면 `data/config.json`(마지막으로 Sheets와 맞춘 사본)을 보여 주고 화면에 안내를 띄웁니다. 이 상태에서는 저장과 자동 처리를 하지 않으며, 연결되면 다시 읽습니다.
- **`data/`** (보존·백업 대상, 다른 서버와 나누지 마세요)

| 파일 | 내용 |
| --- | --- |
| `state.json` | 티켓별 처리 상태, Telegram 전송 기록, PIS 배정 이력(`pis`), Zendesk 접수 기록(`writes`). 접수·알림 중복 방지에 사용 |
| `decision_events.json` | 자동 추천 기록. 정확도 비교의 기준 |
| `evaluation_cases.json`, `prompt_versions.json` | 정확도 비교 결과, 프롬프트 개선 후보 |
| `history.json` | 과거 사례 검색 자료 |
| `usage_events.json` | Claude 호출·토큰 기록 |
| `config.json`, `config_audit.json` | 설정 사본과 변경 이력(최근 200건) |

PostgreSQL은 사용하지 않습니다.

## 안전한 적용 순서

1. 자동 수집을 끈 상태에서 **업무·담당자 기준**을 확인합니다. 파트마다 파트 기본 담당자와 세부업무 담당자를 채우고 **기준 저장**을 누릅니다.
2. **운영 달력**에서 젠콜을 등록합니다(스크린샷으로 채우기 또는 드롭다운 선택 후 **젠콜 저장**).
3. **추천 테스트**에서 가상 문의로 요약·세부업무·개발 담당자·자동 PIS·운영팀 담당자 필드 예상값을 확인합니다. Claude 호출 비용이 발생하며, Telegram 전송을 체크하면 `[테스트]` 메시지가 갑니다.
4. 추천 전용 상태로 자동 수집을 켜고 며칠간 결과를 확인합니다. 쌓인 뒤에는 **검토·정확도**에 접수 현황을 올려 비교합니다.

7. 운영에 적용할 때 `.env`의 Zendesk 계정과 `ALLOW_LIVE_WRITES=true`를 설정하고 재시작한 뒤, 웹에서 실제 접수를 켭니다. 끌 때는 웹 설정만 꺼도 다음 주기부터 멈춥니다.

## 아직 결정·검증이 필요한 사항

- **파트 기본 담당자**: 0.10에서 옮길 때 그 파트 담당이 한 명뿐이던 경우만 채웠습니다. `원무`는 비어 있어 원무 문의(사전심사 화면 문의 포함)가 검토 대상이 됩니다. `진료`·`진료지원`·`보험`도 비어 있습니다.
- **파트 중복**: `기록`·`약제`·`재활`·`영양`이 별도 파트이면서 엑셀에서는 `진료`의 세부업무로도 있습니다. Zendesk 관련파트 옵션 기준으로 정리가 필요합니다.
- **명단에 없는 이름**: 기준표의 `도혜미`, `조한슬(데이터쿼리)`.
- **밀린 티켓 묶음 기준 건수**: '한 번의 조회에서 처리할 대기 건수(최대 10)가 기준 이상'을 한 묶음으로 봅니다. 몇 건부터 묶음으로 볼지는 운영에서 정해 설정하세요.
- 최초 감지 이후 사람이 수정한 티켓과 신규가 아닌 티켓은 이미 사람이 다루는 것으로 보고 PIS를 배정하지 않습니다.
- 계정 기본 양식이 자동으로 붙은 신규 티켓은 '양식 미지정'으로 보고 변경합니다.
- `데이터 서비스` 양식 ID, `등록` 사용자 지정 상태 ID, 양식 필수 필드, 선택값은 실제 계정에서 사전 점검으로 확인해야 합니다. 양식의 다른 필수 필드는 자동으로 채우지 않습니다.

- 실제 스크린샷 인식 정확도, 실제 Zendesk 접수, 실제 브라우저 화면은 미검증입니다.
