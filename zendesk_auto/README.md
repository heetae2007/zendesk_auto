# Zendesk 고객문의 접수 운영실 — 0.1 추천 전용

Linux + Python FastAPI + 웹 관리 화면 + Google Sheets 연결을 위한 첫 구현입니다.
이 버전은 읽기·추천·검토 기록용입니다. **Zendesk 공개 댓글, 담당자, 양식, 상태를 변경하는 코드는 포함하지 않습니다.**
실제 자동 접수는 필드 매핑과 추천 결과를 확인한 후 별도 구현·검증해야 합니다.

## 반영한 운영 기준

- 계정: edgennext.zendesk.com
- 한국시간 평일 09:00 이상 ~18:00 미만 운영. 주말·한국 공휴일 기본 제외.
- 휴무일/운영 시간 외 신규 티켓은 다음 운영일로 보류. 처리 직전 신규 상태 재확인.
- 사내 웹 사용. 외부 Webhook 없이 60초 간격 조회. 감지에는 Zendesk 검색 인덱스 지연이 추가될 수 있습니다.
- 날짜·파트별 주담당/대체 담당자, 병원/키워드별 우선순위 규칙, 제외 날짜를 웹에서 수정.
- 기존 12개 탭 이름을 초기 후보로 등록. 업무·Zendesk ID·선택값은 추정해서 채우지 않음.
- PIS 담당자 입력 제외. PIS가 검토한 분류 오류 피드백만 AI 참고 사례로 사용.
- 별도 Google Sheets 사용. 기존 업무 시트는 변경하지 않음.
- 병원명과 요청부서는 별도 사용자 정의 필드로 매핑. 요청자 이름을 쪼개서 추정하지 않음.

## 1. 로컬 실행

Python 3.11 이상이 필요합니다. 아래는 프로젝트 디렉터리에서 실행합니다.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.lock.txt
cp .env.example .env
```

`.env`의 `ADMIN_PASSWORD`를 충분히 긴 임의 비밀번호로 바꿉니다. `STORE_MODE=local`로 먼저 실행하면 외부 연결 없이 화면·규칙·달력을 점검할 수 있습니다.

```bash
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8080 --workers 1
```

접속: http://127.0.0.1:8080 / 사용자명: `admin` / 비밀번호: `.env`의 값.
원격 Linux 서버라면 SSH 포트 포워딩으로 먼저 확인할 수 있습니다.

```bash
ssh -L 8080:127.0.0.1:8080 사용자명@서버주소
```

실제 사내 공유는 `deploy/nginx.conf.example`을 참고해 사내 HTTPS와 실제 사내망 접근 제한을 적용합니다.
예시 CIDR을 그대로 사용하지 마세요. HTTP Basic 비밀번호는 HTTPS로 보호되어야 합니다.
첫 버전은 단일 관리자 계정이며, 변경 이력 작성자는 `admin`으로 기록됩니다.

## 2. Google Sheets 연결

1. 회사 계정에서 **별도 빈 Google 스프레드시트**를 만듭니다.
2. Google Cloud 프로젝트에서 Google Sheets API를 활성화합니다.
3. 서비스 계정을 만들고 해당 이메일에 새 시트의 편집 권한을 부여합니다.
4. 서버에서 사용할 서비스 계정 JSON을 접근 제한된 `secrets/` 디렉터리에 보관합니다.
5. `.env`에 `STORE_MODE=sheets`, `GOOGLE_SPREADSHEET_ID`, `GOOGLE_APPLICATION_CREDENTIALS`를 설정합니다.
6. 서버를 재시작하고 웹의 **연결 및 설정 → 관리 탭 초기화**를 실행합니다.
7. **과거 사례 → 엑셀 가져오기**에서 비식별화된 기존 파일을 가져옵니다.

시트 주소의 `/d/`와 `/edit` 사이 문자열이 스프레드시트 ID입니다.
관리 탭은 Settings, Agents, Rules, Roster, Calendar, Feedback, Hospitals, History, Decisions입니다.
설정은 웹에서 수정하며 시트에는 ID/JSON/갱신 시각으로 저장합니다. 행을 직접 동시에 수정하지 마세요.
초기화는 없는 탭을 추가하며 기존 설정이 있으면 덮어쓰지 않습니다.
로컬 모드에서 작성한 설정이 새 시트로 자동 이관되지는 않습니다. 실제 설정 입력 전에 Sheets 연결을 마치는 것이 좋습니다.

PostgreSQL/SQL DB는 사용하지 않습니다. Sheets가 설정 원본이며 서버의 `data/`에는 캐시, 작업 커서, 중복 방지 이력, 설정 변경 이력이 저장됩니다.
**data/는 일회성 임시 디렉터리가 아닙니다.** 재시작 간 보존하고 시트와 함께 백업해야 합니다.
하나의 서버·프로세스만 이 시트에 기록해야 합니다. 프로세스 파일 잠금으로 같은 data/의 중복 실행을 거부합니다.

## 3. Zendesk 읽기 연결

`.env`에 Zendesk API 사용이 가능한 계정 이메일과 API 토큰을 설정하고 재시작합니다.
토큰은 소스, 시트, 채팅, 웹 폼에 입력하지 않습니다.

웹의 **연결 및 설정 → Zendesk 필드·양식·상태 조회**를 실행합니다.
확인할 항목:

- 병원명 필드 ID와 옵션의 `value`/표시명 연결
- 요청부서 필드 ID
- 관련파트 필드 ID 및 옵션
- 운영팀 담당자 필드 ID 및 옵션
- 데이터 서비스 양식 ID
- 등록 사용자 지정 상태 ID와 상태 범주

사진의 상단 `담당자`와 하단 `운영팀 담당자`는 동일하다고 가정하지 않습니다.
실제 배정 대상이 어느 필드인지 확인해야 후속 접수 기능을 만들 수 있습니다.
현재 후보의 `Zendesk 사용자 ID` 또는 `운영팀 필드 선택값`은 미해결 업무량 계산에 사용합니다.
설정되지 않은 담당자는 업무량이 정확하지 않으므로 추천 결과의 경고를 확인하세요.

사용 API는 Tickets 조회, Search Export, Ticket Fields, Ticket Forms, Custom Statuses, Groups 조회입니다.
계정 플랜과 역할에 따른 조회 가능 여부를 실제 연결 때 확인합니다.
1분 조회마다 미해결 티켓과 신규 티켓을 조회하며 페이지 제한 초과/오류 시 부분 데이터로 배정하지 않습니다.
검색 인덱스 지연 때문에 실시간 또는 1분 이내 처리를 보장하지 않습니다.

## 4. AI 설정

OpenAI API 프로젝트와 사용 가능한 API 모델을 준비합니다. ChatGPT 웹 창을 자동 조작하는 방식이 아닙니다.
`.env`에 `OPENAI_API_KEY`, `OPENAI_MODEL`을 설정합니다. Structured Outputs를 지원하는 모델이 필요합니다.
의미 검색을 쓰려면 `OPENAI_EMBEDDING_MODEL`도 설정합니다. 미설정 시 문자 2-gram 유사도 검색을 사용합니다.
모델명은 현재 API 프로젝트의 사용 가능 모델을 확인해 입력하세요.

웹에서 외부 AI 분석을 활성화해야 실제 호출합니다. 규칙으로 확정되는 문의는 AI 호출을 생략합니다.
전송 대상은 비식별 문의 문구, 관련 과거 요약, 파트 목록, 검증된 정정 사례입니다. 첨부 이미지/영상은 보내지 않습니다.
주민번호·전화·이메일·명시된 환자명/등록번호의 패턴을 제거하지만 자유 서술에 숨은 모든 개인정보를 검출하지는 못합니다.
실제 데이터로 활성화하기 전에 병원 데이터에 맞는 비식별 검토가 필요합니다. 임베딩도 외부 AI 전송에 해당합니다.
첫 임베딩 색인은 약 2천 건의 추가 호출 비용과 시간이 필요하며 이후 내용 해시로 재사용합니다.
AI confidence는 모델의 자기 평가입니다. 검증 데이터로 자동 접수 허용 기준을 평가하기 전 운영 쓰기를 활성화하면 안 됩니다.

## 5. Telegram

Telegram의 공식 BotFather에서 새 Bot을 만들고 대상 그룹에 추가한 뒤 Bot 토큰과 대화방 ID를 서버 환경변수에 설정합니다.
일반/검토/긴급 후보 모두 `TELEGRAM_CHAT_ID` 한 곳으로 보냅니다. 웹 알림 토글을 켜야 전송합니다.
첫 버전의 알림은 티켓번호와 URL, 추천/검토 상태만 담으며 문의 원문·환자정보를 넣지 않습니다.
전송 응답이 불확실하면 `unknown`으로 기록하고 자동 재전송하지 않습니다. 중복 전송을 피하기 위한 보수적 처리입니다.
웹 상태 API에 전송 상태를 표시합니다. 재전송 관리 UI와 실패별 자동 재시도는 후속 항목입니다.

## 6. 시범 운영 순서

1. Sheets 연결 → 과거 자료 가져오기
2. 12명 후보의 실제 업무 범위와 Zendesk 값 등록
3. 해당 날짜/파트의 담당자·대체 담당자 지정
4. 병원별/업무별 규칙과 휴무일 확인
5. 추천 테스트 화면에서 익명 문의로 검증
6. Zendesk 읽기 연결 후 자동 수집·추천 활성화
7. PIS가 결과를 비교하고 확인된 오류를 피드백으로 등록
8. 검증 후 실제 접수 기능 구현: 안전 업데이트, 수동 변경 보호, 응답 유실 확인, 공개 메시지 중복 방지

## 7. 운영 및 복구

`deploy/zendesk-auto.service`는 /opt/zendesk-auto와 전용 시스템 사용자를 가정한 예시입니다.
설치 담당자가 경로·소유권·자격증명 권한을 맞춘 후 적용하세요. 자동 설치로 서버를 변경하지 않습니다.

```bash
sudo systemctl status zendesk-auto
sudo journalctl -u zendesk-auto -n 100 --no-pager
```

- 중지: 웹에서 자동 분석을 끄거나 `sudo systemctl stop zendesk-auto`.
- 재시작: `data/`를 보존한 상태로 서비스 재시작. 대기 커서와 추천 기록 유지.
- 설정 충돌: 다른 웹 사용자가 먼저 저장했다면 새로고침 후 다시 수정.
- API 오류: 1분 주기에 재시도. 티켓별 분석은 3회 실패 후 검토로 전환.
- 수동 변경 감지: 최초 감지 시각 이후 티켓 변경이 있으면 검토. 재분석 버튼은 관리자가 최신 내용을 확인했다는 명시적 요청으로 취급.
- data 손실: 백업을 복원해야 중복 알림/처리 이력을 보존할 수 있음. Sheets만으로 실행 이력 전체를 자동 복원하는 기능은 아직 없음.
- 여러 서버에서 병렬 실행하지 말 것. 작업량이 커지면 전용 큐와 동시성 저장소로 확장.
